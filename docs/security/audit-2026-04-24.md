### F-001 — FIXED ✅ Usage Limits Now Use Admin Client With Error Checking

**What changed:**

`body-check/route.ts:262` now passes `supabaseAdmin` (service-role client that bypasses RLS) instead of the user-scoped `supabase` client:

```typescript
// body-check/route.ts:262 — FIXED
await incrementUsage(profileId, "ai_photo_analyses", supabaseAdmin);
```

`featureGating.ts:271-286` now checks the return value of the write and throws on failure (both error and zero-rows-affected cases), replacing the previous silent no-op:

```typescript
// featureGating.ts:271-286 — FIXED
const { error, count } = await supabase
  .from("usage_tracking")
  .update({ [columnName]: currentValue + 1, updated_at: new Date().toISOString() })
  .eq("id", existing.id);

if (error) {
  console.error("incrementUsage UPDATE failed", { profileId, columnName, error });
  throw new Error(`Failed to update usage tracking: ${error.message}`);
}
if (count === 0) {
  console.error("incrementUsage UPDATE affected 0 rows", { profileId, columnName });
  throw new Error("Usage tracking update affected 0 rows — possible RLS or missing record");
}
```

**One note:** Supabase JS v2's `.update()` returns `count: null` unless the query includes `{ count: 'exact' }`. The `count === 0` branch will therefore never trigger as written. Since the admin client bypasses RLS this doesn't reintroduce the original bug (writes will succeed), but the guard is currently dead code. Consider adding `{ count: 'exact' }` to the update options if zero-row detection is desired.

**End-to-end verification (2026-05-07):** SMS dispatch test from `/api/dev/send-test-checkin` returned `{ success: true, channel: "sms", providerMessageId: "SM..." }` with confirmed delivery to a registered Twilio trial-account number. The full path — auth → route → `notify()` → dispatcher → `TwilioSMSNotifier` → opt-in check → lazy-init Twilio client → carrier delivery — works as designed.

### F-005 — PARTIALLY FIXED ⚠️ Security Headers Added, CSP Still Missing

`next.config.ts` now emits five security headers on all routes:

```typescript
{ key: "X-Frame-Options", value: "DENY" },
{ key: "X-Content-Type-Options", value: "nosniff" },
{ key: "Referrer-Policy", value: "strict-origin-when-cross-origin" },
{ key: "Strict-Transport-Security", value: "max-age=63072000; includeSubDomains; preload" },
{ key: "Permissions-Policy", value: "camera=(), microphone=(), payment=(self)" },
```

**Still missing: `Content-Security-Policy`.** CSP is the most impactful XSS-mitigation header. It requires auditing all inline scripts, external script/style sources, and image sources before a policy can be drafted. This should be addressed during the restructure (it's a single dedicated pass, but a misconfigured CSP silently breaks Stripe checkout, so it warrants its own focused effort). Starting point for a Next.js + Stripe + Supabase app:

```
Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; connect-src 'self' https://*.supabase.co https://api.stripe.com; frame-src https://js.stripe.com https://hooks.stripe.com; object-src 'none';
```

Tighten from there by removing `unsafe-inline`/`unsafe-eval` once nonces or hashes are applied to inline scripts.

### F-013 — VERIFIED ✅ `client_profiles` RLS Correctly Configured

**Verified directly in Supabase Dashboard on 2026-05-07.**

RLS is **enabled** on `public.client_profiles`. Three policies exist, all targeting the `authenticated` role only (no `anon` access), all properly scoped via `auth.uid()`:

```sql
-- read own profile (SELECT)
USING (user_id = auth.uid())

-- insert own profile (INSERT)
WITH CHECK (user_id = auth.uid())

-- update own profile (UPDATE)
USING (user_id = auth.uid())
WITH CHECK (user_id = auth.uid())
```

The UPDATE policy carries both `USING` and `WITH CHECK` clauses, which closes the row-takeover vector: a user can target only their own row (USING) and the resulting row must still be theirs after the update (WITH CHECK). No DELETE policy exists, which is correct architectural posture — account deletion will go through `supabaseAdmin` server-side as part of F-011's GDPR endpoint.

No wide-open `USING (true)` policy. No `auth.role() = 'authenticated'`-only filter. No anon access.

The most PII-rich table in the schema is correctly locked down.

## Architectural Improvements — Notifier Abstraction

A side effect of the F-002 server-only refactor: the lazy-init work on `twilioClient.ts` and `twilioServer.ts` was used to introduce a generic `Notifier` interface in `src/app/lib/notifications/`. This isolates SMS dispatch behind a channel-agnostic API and prepares the codebase for the eventual mobile push and transactional email channels without committing to either yet.

**Files (new):**
- `src/app/lib/notifications/types.ts` — `Notifier` interface, `NotificationMessage`, `NotifierResult`, `NotificationChannel` union
- `src/app/lib/notifications/twilioSms.ts` — `TwilioSMSNotifier` implementing `Notifier`; performs profile lookup, opt-in check, lazy Twilio client init, and structured error returns
- `src/app/lib/notifications/dispatcher.ts` — `notify(profileId, message)` entry point; selects channel; contains `TODO(mobile)` and `TODO(email)` extension stubs

**Migration scope:** `src/app/api/sms/cron/route.ts` migrated from direct `sendAndLogSms()` calls to `notify()`. Webhook receivers and opt-in/opt-out routes intentionally left untouched (they handle inbound traffic, not proactive sends).

**Why this matters for security:** The dispatcher returns a structured `NotifierResult` with explicit success/failure/skip states. Previously, SMS failures were invisible because the call sites discarded the Twilio SDK response. Now every dispatch produces an inspectable result — which is what allowed end-to-end verification of F-001's fix to actually be performed.

**Future channel additions:** When mobile launches, an `ExpoPushNotifier` (or equivalent) implementing the same `Notifier` interface can be added to the dispatcher's notifier list without modifying any route handler. Same pattern for `ResendEmailNotifier` (or equivalent) when transactional email becomes a priority. Per-user channel preference logic will live inside `dispatcher.ts`, keeping route handlers oblivious to delivery mechanics.

### F-006 — Stripe Event Payloads Stored Verbatim as JSONB
**Severity: MEDIUM | Status: Open (restructure)**

`webhook/route.ts:89-93` is unchanged — `event.data.object` (full Stripe object) is still stored in `stripe_events.payload`:

```typescript
// webhook/route.ts:89-93
await supabaseAdmin.from("stripe_events").insert({
  stripe_event_id: event.id,
  event_type: event.type,
  payload: event.data.object as unknown as Record<string, unknown>,
});
```

Stripe objects include customer email, billing address, and payment-method metadata. This table has no retention policy.

**Remediation (pick one):**
1. Store a whitelist of non-PII fields only (event ID, subscription ID, customer ID, status, amounts).
2. Keep the full payload but add a `pg_cron` job to delete rows older than 90 days.
3. Null out the `payload` column entirely — the idempotency check only needs `stripe_event_id`.

To be designed alongside the broader Comply-stage retention policy during the restructure.

**Effort: S**

### F-008 — Middleware Does Not Enforce Route-Level Auth
**Severity: MEDIUM | Status: Open (restructure)**

`middleware.ts` is unchanged — it only refreshes the session cookie, with no redirect for unauthenticated requests.

This is defence-in-depth, not a standalone vulnerability: every route handler reviewed does perform its own `auth.getUser()` check. The gap is that future routes have no safety net at the middleware layer.

**Remediation (to be implemented during restructure):**

```typescript
// middleware.ts — add after getUser()
const { data: { user } } = await supabase.auth.getUser();
const isPublicPath =
  req.nextUrl.pathname.startsWith("/login") ||
  req.nextUrl.pathname.startsWith("/pricing") ||
  req.nextUrl.pathname === "/" ||
  req.nextUrl.pathname.startsWith("/api/stripe/webhook") ||
  req.nextUrl.pathname.startsWith("/api/sms/webhook") ||
  req.nextUrl.pathname.startsWith("/api/sms/cron");

if (!user && !isPublicPath) {
  return NextResponse.redirect(new URL("/login", req.url));
}
```

**Effort: S**

9. **`count` option in `incrementUsage`** — The `count === 0` guard in `featureGating.ts` will always evaluate to false because Supabase's `.update()` returns `count: null` without `{ count: 'exact' }`. Decide whether to add that option or remove the dead guard.

## Methodology Note

This document is the historical record for the audit conducted on 2026-04-24, annotated with resolution status as of 2026-05-07. **Future audits will be issued as separate datestamped files** (`docs/security/audit-YYYY-MM-DD.md`) so this document remains a snapshot rather than a moving target. Audit-on-audit diffs over time become the evidence trail for the Govern stage of the security framework, and the basis for any future compliance conversations.

The recommended audit cadence is: monthly during active development, immediately before any major launch, and immediately following any suspected security event. Each audit should produce its own datestamped file regardless of how much (or little) has changed since the previous one — the empty audit ("nothing of note") is itself a valuable signal.
